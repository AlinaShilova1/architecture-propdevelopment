Требования к безопасности:
1. Разделение ответственности за биометрию: распознавание лиц полностью на стороне партнёра. PropDevelopment не хранит шаблоны биометрии; внутри компании — только идентификаторы и факты событий (минимизация данных).
2. Шифрование трафика: HTTPS TLS ≥ 1.2, обязательный mTLS для «сервер-сервер».
3. Подписанные вебхуки: все входящие события подписаны (HMAC-SHA256 или JWS). Проверка подписи и replay-защита (timestamp, nonce), идемпотентность по event_id.
4. Секреты и ключи: хранение только в KMS/Secrets (Vault/KMS), ротация, разделение прав (RBAC), запрет логирования секретов.
5. Изоляция периметра: IP-allowlist/зоны, rate limiting/Ddos-защита на шлюзе, WAF/бот-защита для конечных точек.
6. Политики доступа: ABAC на уровне tenant-core (дом/подъезд/квартира/ТС/роль пользователя/временные окна). Никаких «широких» скоупов.
7. Журналы и трейсы: централизованное логирование, трассировка (корреляционные ID), хранение аудита действий по требованиям законодательства.
8. Конфиденциальность: минимизация полей событий, маскирование чувствительных атрибутов в логах.

Протоколы аутентификации и авторизации:
1. Мобильное приложение ↔ PropDevelopment: OIDC/OAuth2.1, IdP — Keycloak. Скоупы только под требуемые операции (least privilege).
2. PropDevelopment сервисы ↔ Партнёр: OAuth2 Client Credentials (machine-to-machine) для вызова API партнёра; альтернативно JWT-client assertion.
3. mTLS на транспортном уровне.
4. Внутри PropDevelopment: сервис-к-сервису — короткоживущие сервисные токены (STS), mutual TLS, авторизация на шлюзе.

Интеграционные потоки:
1. Контракты OpenAPI/AsyncAPI, версии v1, v2 с параллельной поддержкой и сроками депрекации.
2. Каждое событие/команда содержит correlation_id, event_id, occurred_at, ttl, schema_version.

Надёжность и производительность:
1. Ретраи (идемпотентные), лимиты QPS, квоты per-tenant.
2. Тестовые стенды/песочницы, тестовые сертификаты/секреты.

Наблюдаемость и управление:
1. Дашборды: приём вебхуков, время обработки, отказ/ретраи, распределение статусов.
2. Алерты: SLO по латентности, ошибкам подписи, росту ретраев, превышению квот.
3. Безопасная деградация: при недоступности партнёра — ручной режим (вызов консьержа/охранника), UI-пояснение пользователю и регистрация инцидента.
